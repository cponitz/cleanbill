## 2. Problem

Every customer message is copied by hand into a mail client. That does not scale past the walkthrough, loses `sent_at` (so the funnel and the agent cannot see what was sent), and cannot attach the packet for the `ready_to_submit` "please review" message.

## 3. Behaviour (operator)

1. In the `/ops` claim drawer, every approved, unsent outbound e-mail shows **Send** next to **Copy**. Send → the message goes out from `Clean Bill <hello@cleanbillco.com>` wrapped in the Clean Bill template; the row turns "sent · 14:02" with the provider id; **Copy** stays.
2. For `intent = ready_to_submit` (and `filed` when a filing has a packet), the claim's packet PDF is attached (`Form-50-114-<code>.pdf`).
3. Drafts (`agent_draft=true`) cannot be sent — Approve first (two clicks on purpose; shadow mode B-10). A message with no `customers.email` shows Send disabled with "no e-mail on the account".
4. Delivery state comes back by webhook and shows on the row: delivered / bounced / complained, with the reason on hover; a bounce sets a warning badge on the claim in the list.
5. When the Resend flag is off, Send is hidden and the "copy it into your mail client" line stays — nothing else changes.
6. Replies go to `hello@cleanbillco.com` (`reply_to`), which is a human inbox for the test (O-08). Inbound e-mail parsing is out of scope.

## 4. Design

### 4.1 One template, two renderers, one parity test

- `python -m cleanbill.brand --sync` additionally generates **`supabase/functions/_shared/email_template.ts`**: `export const EMAIL_BASE_HTML = "…"` (the contents of `cleanbill/email/base.html`) plus the disclaimer and support strings. CI's `--sync --check` fails when stale (same mechanism as `brand.ts`).
- New `supabase/functions/_shared/email.ts`: `renderEmail(subject, body, opts?) -> {html, text}` — a line-for-line port of `cleanbill/email/__init__.py` (`_paragraphs`, `body_to_html`, `text_alternative`, the `{{key}}` substitution).
- **Parity test** (ADR 0016 pattern): `tests/fixtures/email_snapshot.json` holds `{subject, body}` inputs and the Python output; `tests/test_brand.py` regenerates and compares; `_shared/email_test.ts` renders the same inputs and asserts byte equality. Both suites run in CI; a template edit changes the snapshot in the same PR.

### 4.2 `POST /ops {action: "send", message_id}` (in `supabase/functions/ops/index.ts`, guards in `logic.ts`)

1. Guards (`logic.ts`, unit-tested): message exists; `direction='outbound'`; `channel='email'`; `agent_draft=false`; `sent_at` null; the claim's account has an e-mail; `RESEND_ENABLED === "true"` else 409 `send_disabled`; concurrent double-click → the second call sees `sent_at` set (update `… where sent_at is null` and check the row count) and returns `already_sent`.
2. Render with `renderEmail(subject, body)`. Personalisation is already in the draft body (the agent fills `{{first_name}}` etc. when drafting); the send does no substitution.
3. Attachment: for `intent in ('ready_to_submit','filed')` with a `filings.packet_path` → download from the `packets` bucket with the service client, base64, `attachments: [{filename, content}]`; refuse (`packet_too_large`) above 20 MB (Resend's limit is 40 MB after base64).
4. `POST https://api.resend.com/emails` with `Authorization: Bearer $RESEND_API_KEY`, header `Idempotency-Key: msg-<message_id>` (Resend keeps it 24 h; combined with guard 1 this makes double sends impossible), body `{from: "Clean Bill <hello@cleanbillco.com>", to: [email], reply_to: "hello@cleanbillco.com", subject, html, text, attachments?, tags: [{name:"intent", value}, {name:"claim_code", value}], headers: {"X-Entity-Ref-ID": message_id}}`. `from` and `reply_to` come from `SUPPORT_EMAIL` / `BRAND` in `_shared/db.ts` — no new literal.
5. On 2xx: `messages.sent_at=now()`, `provider='resend'`, `provider_message_id=<id>`, `delivery_status='sent'`; audit row `message_send` with `{resend_id, attached: bool}`; respond `{ok:true, sent_at, provider_message_id}`. On Resend error: no DB change except audit `message_send_failed {status, error}`; respond `{ok:false, error:"provider_error", message}`. Timeout 20 s.
6. `GET /ops` gains `features: {resend: boolean, stripe: boolean, lob: boolean}` (read from the secrets; SPEC-03 and SPEC-11 fill the other two) and, per message, `provider_message_id`, `delivery_status`, `delivery_detail`.

### 4.3 Webhooks — new edge function `supabase/functions/webhooks` (shared with SPEC-11)

- Route `POST /webhooks/resend`. `verify_jwt=false` in `config.toml` (providers cannot send a Supabase JWT). Verify the **Svix** signature Resend uses (`svix-id`, `svix-timestamp`, `svix-signature` headers, HMAC-SHA256 over `id.timestamp.body` with `RESEND_WEBHOOK_SECRET`, base64; reject > 5 min skew) — implemented in `_shared/webhook_sig.ts` with Deno tests (good signature, bad signature, stale timestamp).
- Events handled: `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, `email.opened` (if tracking is on — it is **off** by default; keep it off: no open/click tracking on customer mail, ADR note). Look up `messages` by `provider_message_id = data.email_id`; set `delivery_status` (`sent|delivered|delayed|bounced|complained`), append `{type, at, detail}` to `delivery_detail` (jsonb array); on `bounced`/`complained` also insert `events` kind `email_bounced` / `email_complained` with the claim code so the `/ops` funnel and the claim list badge see it. Unknown ids → 200 (log, no error — Resend retries on non-2xx).
- The webhook itself is registered **by Claude Code through Resend's API** (`POST https://api.resend.com/webhooks {endpoint, events}`) once the function is deployed; the returned signing secret is set with `supabase secrets set RESEND_WEBHOOK_SECRET=…`. No dashboard clicks for Charlie.

### 4.4 `/ops` page (`Ops.tsx`)

- **Send** button (`data-testid="btn-send"`) on approved unsent outbound e-mails when `features.resend`; busy state; success → row shows "sent · time · delivered/bounced" from the message fields; error banner with the API message. Bounce → `badge-bad` "bounced" on the row and a small warning on the claim in the list (same `badge` component, status map untouched).
- Health section gains a **Mail** line: `features.resend` on/off, last webhook received (from a `system_status` row `resend_webhook` the function writes on every event).
- Smoke scenario E gains: with `RESEND_ENABLED=true` and `SMOKE_INBOX` (an address Charlie controls) in `.env`, approve then send the synthetic claim's draft to that inbox and assert `sent_at` in `GET /ops`; skipped when either is missing.

### 4.5 Sending domain

Resend recommends a subdomain for reputation isolation; B-19 requires the visible address `hello@cleanbillco.com`. Resolution: **verify the root domain `cleanbillco.com` in Resend** (so `from` is exactly hello@) with the **Return-Path on the `send` subdomain** (Resend's default) — that gives DKIM + SPF on Resend's own subdomain and leaves the root MX free for the human mailbox. DMARC `p=none` first; tighten to `quarantine` after the test when reports show only Resend and the mailbox provider sending. Records are in §7.

## 5. Data changes

Migration `2026MMDDHHMMSS_messages_delivery.sql`: `messages` add `provider text check (provider in ('resend'))`, `provider_message_id text unique`, `delivery_status text check (delivery_status in ('sent','delivered','delayed','bounced','complained'))`, `delivery_detail jsonb not null default '[]'`; index on `provider_message_id`. `events.kind` gains `email_bounced`, `email_complained` (no constraint to change). `supabase/ci/check_schema.sql` asserts the columns. `docs/ARCHITECTURE.md` §3.1 (new row: `webhooks` function), §4.1 (`messages`), §5 (ops flow: send; new inbound-webhook flow) updated; ADR 0022 "Outbound e-mail: operator-initiated Resend send from the ops API, one template rendered identically in Python and TypeScript, delivery state by signed webhook, root domain verified with Return-Path on `send.`".

## 8. Acceptance

1. An approved `ready_to_submit` message for the synthetic claim sends from `Clean Bill <hello@cleanbillco.com>` to `SMOKE_INBOX` with the packet attached; the HTML matches the `/design-system` e-mail preview; the text alternative is present; the mail passes DKIM and SPF (Gmail "Show original" shows `PASS` for both) and DMARC.
2. `messages.sent_at`, `provider_message_id`, `delivery_status='delivered'` set; `audit_log` has `message_send`; `/ops` row shows "sent · delivered".
3. Sending a draft, an already-sent message, an inbound message, or with the flag off is refused with the named error (Deno tests + curl).
4. Double-click sends once (guard + Idempotency-Key; test with two concurrent requests).
5. A webhook with a bad signature is rejected 401 and logged; a bounce webhook sets `bounced`, appends detail, writes the `email_bounced` event and the badge appears.
6. Python and TypeScript renderers produce byte-identical output for every fixture; `--sync --check` guards staleness.
7. No open- or click-tracking; no customer e-mail is sent by anything other than the operator's Send (grep: the only Resend call site is the `send` action).
8. Smoke E (flag off and flag on) green; migration applied; schema parity empty; CHANGELOG, ARCHITECTURE, ADR 0022, RUNBOOK, glossary updated.

## 10. Glossary

**API** application programming interface · **Base64** text encoding used to put a file inside JSON · **B-nn / O-nn / G-nn** business decision / open decision / gap-register item · **Bounce** the receiving server rejected the message (bad address, full box) · **Complaint** the recipient marked the mail as spam · **DKIM** DomainKeys Identified Mail — a cryptographic signature proving the mail came from the domain · **DMARC** Domain-based Message Authentication, Reporting and Conformance — the policy record telling receivers what to do when SPF/DKIM fail, and where to send reports · **DNS** the domain name system — the records for `cleanbillco.com`, hosted at Vercel · **Edge function** a small server program on Supabase at a public URL · **HMAC-SHA256** the keyed hash used to sign webhook payloads · **Idempotency-Key** a header that makes a repeated API call return the first result instead of acting twice · **Intent** the purpose label on a `messages` row (`ready_to_submit`, `filed`, …) · **MX record** the DNS record naming the server that receives mail for a domain · **Packet** the filled, signed Form 50-114 PDF · **Return-Path** the address bounces go to; Resend puts it on a subdomain (`send.cleanbillco.com`) · **Resend** the transactional e-mail API · **Shadow mode** the agent drafts, a human approves (B-10) · **SPF** Sender Policy Framework — the DNS record listing servers allowed to send for a domain · **Svix** the webhook-delivery service Resend uses; its signature scheme is what the endpoint verifies · **Webhook** an HTTP call a provider makes to us when something happens (delivered, bounced) · **§41.0051** the Property Code advertisement disclaimer rule (in every e-mail footer).
