## 2. Problem

The first 1,000-piece mailing (B-07's kill test) needs a repeatable, auditable way to pick leads, render their letters, verify addresses, hand them to Lob, and record what was mailed so the funnel, the claim page and the agent all know a letter went out. Nothing today writes `mailed`.

## 3. Behaviour (operator)

1. **Dry run.** `python -m cleanbill.letters.batch --batch 2026-10-05-t1 --tier 1 --n 1000 --variant-split 50 --seed 20261005 --dry-run` prints the batch summary (counts by value band, variant, city and taxing unit; median and total estimate; excluded counts by reason; undeliverable count after address verification; estimated cost) and writes `data/out/batches/2026-10-05-t1.csv` (git-ignored: real names) plus 10 rendered sample PDFs for review. Nothing is written to the database.
2. **Proof.** `--n 5 --to-override "<Charlie's address>" --send` with the **live** key mails five real letters (three A, two B, different leads' content) to Charlie so he holds the piece before 1,000 go out. Rows are written to `mail_pieces` with `batch='proof-…'` and the leads are **not** marked mailed (`--to-override` never touches `leads`).
3. **Send.** The same command without `--dry-run` and with `--send`: renders each letter, verifies the address with Lob, creates the Lob letter, writes a `mail_pieces` row and sets `leads.status='mailed'`, `mailed_at`, `letter_variant`. Resumable: re-running the same `--batch` skips leads that already have a `mail_pieces` row for it (Lob Idempotency-Key per piece makes the API side safe too).
4. **Watch.** `/ops` Funnel gains three tiles from `mail_pieces`: mailed · delivered · returned; Health gains a **Mail** line (last batch, pieces, last webhook). A returned letter suppresses the lead (`status='suppressed'`) so it is never re-mailed.
5. **Guard rails that cannot be switched off by a flag:** never an `estimate_unconfirmed` lead (B-18) · never a lead already `mailed`/`opened`/`claimed`/… · never `hs_exempt` · never `address_suppressed` · never the synthetic account · never with a live key unless `LOB_ENABLED=true` **and** `--send` **and** the footer entity line was confirmed on the command line (`--confirm-footer "Clean Bill Co."` must equal `brand.LEGAL_NAME`).

## 4. Design

### 4.1 `cleanbill/letters/batch.py` (new; runs on the Mac from the repo folder, like `publish.py`)

**Selection** (Supabase service client, paged reads of `leads` joined to `properties` — the published table, not the roll; the roll is not needed):

```
tier = --tier (default 1) · status = 'new' · mailed_at is null · estimate_unconfirmed = false
· properties.hs_exempt = false · properties.address_suppressed = false · prop_id ≠ 999000001 · claim_code not like 'CB-TEST-%'
· owner mailing address complete (addr1, city, state='TX', 5-digit zip) · not in --exclude-file (a CSV of prop_ids: opt-outs, Charlie's own home, friends' walkthrough properties)
```

**Stratified sample** by value band on `properties.market_value` — bands `100–200k`, `200–350k`, `350–500k`, `500–750k`, `750k+` — proportional to the eligible population (the test measures the whole Tier-1 list's response, so the sample must look like the list), seeded (`--seed`) so a dry run and its send pick the same leads. Within each band, variants alternate A/B (`--variant-split 50` = 50% A). `--cap-per-band` optional. The summary prints, per band and variant: n, median estimate, share of each city and each taxing unit, so a skewed draw is visible before anything is sent.

**Address verification** — `POST https://api.lob.com/v1/us_verifications` per selected lead (`primary_line`, `secondary_line`, `city`, `state`, `zip_code`): keep `deliverability in ('deliverable','deliverable_unnecessary_unit')` and use the **verified components** Lob returns for the envelope; `deliverable_incorrect_unit` / `deliverable_missing_unit` / `undeliverable` → excluded from this batch, recorded in `mail_pieces` with `status='address_rejected'` and the verification JSON, and the lead left `new` (the ETL's mailing==situs rule already removes most unit problems; expect < 2%). Run in the dry run too, so the summary's undeliverable count is real (verification with the test key returns fixed fixtures — use the live key for the real dry run; verifications are priced per lookup, ~1,000 lookups is a few dollars).

**Render** — `render_letter` unchanged except two additions: (a) the recipient block uses Lob's verified components; (b) the return-address / entity line reads `brand.LEGAL_NAME` and a new `brand.RETURN_ADDRESS` (see §5). Each PDF's SHA-256 goes in `mail_pieces.pdf_sha256`; PDFs are kept under `data/out/batches/<batch>/` (git-ignored) for the audit trail, not uploaded to Supabase (real names; ADR 0007 spirit).

**Lob letter** — `POST https://api.lob.com/v1/letters` (multipart: `file` = the PDF; `to` inline = the verified components + `name` = owner name; `from` inline = `brand.RETURN_ADDRESS`; `color=false`; `double_sided=false`; `address_placement=top_first_page`; `mail_type=usps_first_class`; `use_type=marketing` (Lob requires the use type; this is an advertisement under §41.0051); `description="<batch>:<claim_code>"`; `metadata[claim_code]`, `[batch]`, `[variant]`, `[tier]`; header `Idempotency-Key: <batch>:<claim_code>`). Response `id` (`ltr_…`), `expected_delivery_date`, `url` (30-day signed PDF) → `mail_pieces`. Throttle 5 requests/s; honour `429` + `Retry-After`; on any error after 3 retries stop the run and print the resume command (nothing is half-written: the `mail_pieces` row is inserted only after Lob's 200, and `leads` is updated in the same transaction-equivalent step).

**Flags** — `LOB_API_KEY` (test `test_…` or live `live_…`), `LOB_ENABLED` (`true` required for `--send` with a live key; a test key never needs it — test letters are free and not mailed), both in the Mac `.env`. The CLI prints which mode it is in on the first line and refuses `--send` with a live key when `LOB_ENABLED` is not `true`, when `--confirm-footer` does not match `brand.LEGAL_NAME`, or when `brand.RETURN_ADDRESS` is still the placeholder.

**Address-window compliance (the unverified part of "Lob-ready")** — before the proof, render one letter through Lob **test mode**, download the returned PDF and thumbnails, and check the recipient block sits inside Lob's `top_first_page` window zone with nothing else in it, and that all content clears the 1/16 in ink-free border. If it does not, move the block (a constant in `generate.py`) — do **not** switch to `insert_blank_page` (an extra page fee on 1,000 pieces) unless the layout cannot be made to fit. Record the check (thumbnail in the PR) in `docs/reports/2026-09-xx-lob-proof.md`.

### 4.2 Webhooks — route `POST /webhooks/lob` in the `webhooks` function (SPEC-10 §4.3)

- Verify Lob's signature: headers `Lob-Signature` (hex HMAC-SHA256 of `"<Lob-Signature-Timestamp>.<raw body>"` with the webhook secret) and `Lob-Signature-Timestamp`; reject > 5 min skew — confirm the exact scheme against Lob's webhook docs when implementing and pin it in `_shared/webhook_sig.ts` next to the Svix verifier, with tests.
- Events subscribed: `letter.created`, `letter.rendered_pdf`, `letter.mailed`, `letter.in_transit`, `letter.in_local_area`, `letter.processed_for_delivery`, `letter.re-routed`, `letter.returned_to_sender`, `letter.deleted`. Look up `mail_pieces` by `lob_id = body.reference_id`; append `{type, at, detail}` to `events`; set `status` to the latest milestone (`created → rendered → mailed → in_transit → in_local_area → processed_for_delivery`; `returned_to_sender`, `re_routed`, `deleted` as terminal/side states). `processed_for_delivery` → `mail_pieces.delivered_at`; `returned_to_sender` → `leads.status='suppressed'` + `events` kind `mail_returned` with the claim code (funnel-visible). Write `system_status` row `lob_webhook` on every event. Unknown ids → 200 and a log line.
- Test mode emits `letter.created` / `rendered_pdf` only; tracking events arrive only for live pieces — the proof is the first end-to-end webhook test.

### 4.3 `/ops` additions (small)

- `GET /ops`: `kpis.mailed` now counts `mail_pieces` with `status not in ('address_rejected','deleted')` and `to_override=false` (the lead count stays as a cross-check in `funnel`); new `kpis.delivered`, `kpis.returned`; `system` gains the `lob_webhook` row; `mail: {batches: [{batch, n, sent_at, delivered, returned}]}` (SQL group by).
- `Ops.tsx`: three tiles; a **Mail** line under Health listing batches. No new components; existing `.kpi` / `.table`.
- Claim drawer: the lead's `letter_variant` and `mailed_at` in the property line ("Letter B · mailed Oct 5 · delivered Oct 9"), so a claim's origin is visible.

## 10. Glossary

**A/B variant** the two letter wordings (`copy/letter_variant_a.md`, `_b.md`) mailed in equal halves to compare response · **Address verification** Lob's check that USPS can deliver to an address, returning corrected components · **B-nn / O-nn / G-nn** business decision / open decision / gap-register item · **Batch** one named run of the mailing command (`2026-10-05-t1`) · **Deliverability** Lob's verdict per address (`deliverable`, `deliverable_unnecessary_unit`, `deliverable_incorrect_unit`, `deliverable_missing_unit`, `undeliverable`) · **DPV** USPS Delivery Point Validation, the basis of that verdict · **Edge function** a small server program on Supabase at a public URL · **ESD / MUD / WCID** emergency services district / municipal utility district / water control and improvement district — small taxing units · **First Class** USPS mail class, 3–5 business days · **HMAC-SHA256** the keyed hash used to sign webhook payloads · **Idempotency-Key** a header that makes a repeated API call return the first result instead of acting twice · **Ink-free zone** the border and window area Lob requires empty on the first page · **Lob** the print-and-mail API · **`mail_pieces`** the new table with one row per letter Lob was asked to print · **Proof** a small live send to Charlie's own address before the batch · **QR code** the scannable square on the letter linking to the claim page · **Return address** the sender address on the envelope; undeliverable mail comes back to it · **Seed** the number that makes a random draw reproducible · **Stratified sample** a draw that keeps each value band's share equal to its share of the whole list · **Test mode / test key** Lob's sandbox: letters are rendered, nothing is printed or charged · **Tier 1** leads that owned the home before Jan 1 of the earliest refundable year (both years claimable) · **`top_first_page`** Lob's option to print the recipient address on our first page (vs. `insert_blank_page`, an extra sheet) · **`use_type`** Lob's required label — `marketing` for advertisements · **Value band** a market-value range used for stratification · **Webhook** an HTTP call a provider makes to us when something happens (mailed, delivered, returned) · **§41.0051** Texas Property Code rule requiring the advertisement disclaimer and the naming of the taxing units on solicitations.
